# Gemini 답변 생성 평가 기준선
> 역사적 단계 기록: 이 문서는 개발 당시의 구현과 수치를 보존한다. 현재 상태와 실행 방법은 [프로젝트 README](../README.md) 및 [문서 지도](README.md)를 기준으로 한다.


## 왜 평가하는가

검색기가 관련 문장을 찾는 것과 LLM이 그 근거로 정확한 답을 만드는 것은 서로 다른 문제다. 따라서 검색 평가는 `정답 근거를 찾았는가`, 생성 평가는 `찾은 근거로 정확히 답하고 출처를 밝혔는가`를 따로 측정한다.

## 평가 방법

- 모델: `gemini-3.5-flash-lite`
- 데이터: 2026-2학기 수강편람 기반 질문 15개
- context: 검색 상위 3개, 인접 범위 ±1, 최대 6 chunks·6,000자
- 자동 검사: 질문별 핵심 답값, 기대 PDF 페이지 인용, 세종대학교 공식 URL
- 수동 검사: 답변을 검색 근거와 대조해 사실 왜곡이나 근거 없는 단정이 있는지 확인
- 실행 명령: `.venv/bin/sejong-evaluate-generation`
- 결과 파일: `data/evaluation/gemini-3.5-flash-lite-answers.jsonl` (Git 제외)

## 결과

| 지표 | 결과 |
|---|---:|
| API 호출 성공 | 15/15 |
| 핵심 답값 통과 | 15/15 (100%) |
| 기대 페이지 인용 | 15/15 (100%) |
| 공식 출처 URL 포함 | 15/15 (100%) |
| 자동 검사 전체 통과 | 15/15 (100%) |
| 수동 근거 검토 통과 | 15/15 |
| 입력 tokens | 54,019 |
| 출력 tokens | 1,689 |
| 전체 tokens | 55,708 |
| 질문당 평균 전체 tokens | 3,713.9 |

입력이 전체 token의 대부분이다. 즉 비용과 지연 시간을 줄이려면 답변을 억지로 짧게 만드는 것보다 관련 없는 context를 덜 보내는 개선이 중요하다.

## 평가기에서 발견한 문제

첫 채점은 13/15였다. 그러나 실패 답변을 직접 확인하니 모델 오류가 아니라 평가기 오류였다.

1. 개강일 답변은 `[p. 3, p. 5]`라고 올바르게 인용했지만, 평가기가 `[p. 5]`처럼 페이지가 하나인 형식만 허용했다. 대괄호 안의 모든 `p.숫자`를 읽도록 수정했다.
2. K-MOOC 질문은 `졸업할 때까지 몇 학점`만 물었는데 기대값이 학기당 3학점까지 동시에 요구했다. 질문 범위에 맞게 졸업 한도 6학점만 검사하도록 수정했다.

이 사례는 자동 평가 점수가 낮을 때 곧바로 모델 실패라고 결론 내리지 말고, 검색·생성·평가 규칙 중 어디가 원인인지 분리해야 함을 보여준다.

## 한계

- 15개뿐인 작은 내부 평가셋이며 모두 같은 수강편람에서 만들었다.
- 질문 작성과 시스템 개발이 분리되지 않아 평가셋 과적합 가능성이 있다.
- 핵심 문자열 검사는 의미가 틀린 문장 속에 해당 문자열이 있어도 통과할 수 있다.
- 각 질문을 한 번씩만 호출해 생성 결과의 변동성을 측정하지 않았다.
- 수동 검토는 독립적인 학교 행정 전문가 검수가 아니다.
- 장학금 공지, 졸업요건, 학과 공지 등 다른 문서 유형의 성능을 대표하지 않는다.

따라서 이번 100%는 `현재 15개 수강편람 질문에 대한 기준선`이지, 세종대학교의 모든 질문에 100% 정확하다는 뜻이 아니다.
