# 첨부파일 텍스트 추출 결과

## 청크 선별·완전 일치 첨부 중복 처리 (2026-10-10)

실행: `.venv/bin/python -m sejong_rag.select_chunks`.
입력은 정리본과 `structured-chunks`, 출력은 새 폴더 `data/processed/selected-chunks`다.
기존 출력 폴더는 덮어쓰지 않는다. 임베딩·검색 인덱스 변경은 하지 않는다.

1. 원본 첨부의 SHA-256(파일 내용 지문)을 직접 다시 계산한다.
2. 지문이 같은 원본은 바이트를 실제 비교해 완전 일치 여부를 확인한다.
3. 일반 추출 청크에 쓰이는 추출문과 구조 위치도 비교한다. 원본이 같아도
   추출문이 다르면 별도 대표로 남긴다. 이번 자료에서는 이 예외가 없었다.
4. 일치 그룹에서 사용 가능한 첨부 ID의 사전순 첫 항목을 대표로 고른다.
   최신 자료라는 의미는 아니다. 다른 공지의 제목·게시일·주소·첨부 주소는
   `source_aliases`에 모두 남긴다. 대표 제목을 모든 공지의 제목으로 해석하면 안 된다.

선택 대상은 `ready.jsonl`뿐이다. 원본 첨부 381개는 275종류이고,
중복 그룹 58개에 추가 사본 106개가 있었다. 실제 일반 추출 청크가 있는
첨부 344개는 대표 242개로 묶였다. 청크는 52,239개에서 33,734개로 선별됐고,
18,505개가 중복 사본으로 사용 목록에서 제외됐다.
검토 대기 9,462개와 잡음 의심 735개는 기존 폴더에 그대로 남겨 뒀다.

- `selected.jsonl`: 다음 임베딩 단계의 후보 청크. 출처 별칭 포함.
- `omitted-duplicates.jsonl`: 제외된 청크와 대표 첨부 연결 기록.
- `attachment-groups.jsonl`: 검토 대기를 포함한 전체 원본 일치 그룹과 출처.
- `report.json`: 수치·예외·입력 내용 지문과 정책.

원본 파일·기존 청크는 삭제하지 않는다. 공지 본문, 유사 문서, 문서 내부의 반복 문구는
중복 제거하지 않는다. ZIP은 압축파일 전체 바이트를 비교하며 내부 파일별 비교는 하지 않는다.
따라서 눈에 보이는 내용이 같아도 PDF 내부 속성이나 압축 방식이 다르면 별개로 남을 수 있다.
이 단계는 잘못 합치는 위험을 줄이려는 보수적 처리다.

## 정리본 기반 청킹 (2026-10-10)

실행: `.venv/bin/python -m sejong_rag.structure_chunk`.
입력은 `data/processed/normalized-text/records.jsonl`, 새 출력 폴더는
`data/processed/structured-chunks`다. 기존 검색 인덱스에는 연결하지 않았고 임베딩은 실행하지 않는다.
같은 출력 폴더를 덮어쓰지 않으며, 재실행 시 `--output-dir`로 새 경로를 지정한다.

- 저장된 `intfloat/multilingual-e5-small` 토크나이저를 오프라인으로 사용한다.
- 제목·파일명·표 참고 문구·특수 토큰을 포함해 최대 448토큰이다.
- 긴 항목을 나눌 때 문장·줄 경계를 우선하고, 원문 토큰 위치 기준 최대 64토큰을 겹친다.
  별개의 항목이나 문서를 무조건 겹치지는 않는다.
- 번호·소제목을 규칙으로 감지하며 `※`, `단,`, `다만` 등의 문장을 앞 항목에 둔다.
  의미를 이해하는 AI 판단이 아니므로 구조가 손상된 문서는 오분할 가능성이 있다.
- 서로 다른 문서·ZIP 내부 파일·페이지·시트·표·검토 계층은 합치지 않는다.
  페이지를 넘는 문맥은 자동으로 연결하지 않는 보수적 구현이다.
- 표에는 같은 그룹의 첫 3개 기록에서 최대 70토큰의 참고 문구를 붙인다.
  실제 열 제목이라고 판정한 것이 아니며, 복잡한 표의 열-값 관계 복원은 하지 않는다.
- 제목과 파일명도 입력 길이를 제한하지만 전체 메타데이터는 별도 필드로 보존한다.
- 각 조각의 원래 기록 번호, 문자 시작·끝 위치, 원문 위치를 `source_spans`에 저장한다.
  표 참고 문구의 원래 기록 번호는 `context_record_ids`에 남긴다.

출력은 `ready.jsonl`(기존 추출 성공), `review.jsonl`(검토 대기),
`quarantine.jsonl`(잡음 의심), `skipped.jsonl`(빈 텍스트)로 구분한다.
`ready`도 사실 정확성이나 사람의 검토 완료를 보증하지 않는다.
개별 페이지가 확인됐더라도 문서 전체의 검토 상태는 자동 승격하지 않는다.
원문 내 비공백 문자 누락 여부·청크 번호 중복·길이 한도·입력 불변을 검사한다.
결과 개수와 샘플은 출력 폴더의 `report.json`을 참고한다.

이번 실행: 입력 92,029개 기록에서 빈 기록 10개를 제외하고 청크 62,436개 생성.
일반 추출 자료 52,239개, 검토 대기 9,462개, 잡음 의심 735개로 분리했다.
토큰 수는 최소 14, 중앙값 305, 평균 261.9, 최대 448이다.
전체 청크의 고유 번호·출처·원문 위치·길이를 확인하고 표본 64개의 토큰 수를
독립적으로 다시 계산했다. 자동 테스트는 189개 통과했다.
이 개수는 중복 첨부를 제거하기 전 수치이며, 최종 임베딩 개수와 같다는 뜻은 아니다.

이전에 만들어 둔 검색 파이프라인을 그대로 실행하면 새 청크가 자동 사용되지는 않는다.
다음 임베딩 단계에서 사용할 계층과 입력 형식을 명시적으로 연결해야 한다.

## 텍스트 정리 단계 (2026-10-10)

텍스트 추출은 파일에서 글자를 꺼내는 일이고, 정리는 그 글자의 표현 형식을
통일하는 일이다. 요약·오탈자 추측 수정·검토 완료 판정은 하지 않는다.
현재는 학습을 위해 남은 원본 대조를 보류하고 보수적인 정리본을 별도로 생성했다.

실행 명령:

    .venv/bin/python -m sejong_rag.normalize_text --output-dir data/processed/normalized-text

이미 존재하는 출력 폴더는 덮어쓰지 않는다. 다시 실행하려면 새로운 출력 폴더를 지정한다.

- `records.jsonl`: 공지 본문·첨부·이미지를 동일한 필드 구조로 모은 정리 기록.
- `documents.jsonl`: 본문 유무, 원래 추출 보고서·경고, 글을 확보하지 못한 이미지도 보존한 목록.
- `report.json`: 적용 규칙·변경 수·주의 표시·전후 예시·입력 파일 내용 지문.

JSONL은 한 줄에 한 개의 JSON 기록을 저장하는 형식이다. 여기서 기록은
페이지·문단·표 행 등 기존 추출 단위이며, 검색을 위한 청크가 아니다.

### 적용 규칙과 보존 기준

1. 한글 등의 유니코드 조합을 NFC 방식으로 통일한다. 원문 기호 `Ⅰ`, `①`는 유지한다.
2. 운영체제별 줄바꿈을 통일하고, 특수 공백을 일반 공백으로 바꾼다.
3. 파일 맨 앞의 BOM(문자 인코딩 표시), 줄 끝 공백, 과도한 빈 줄만 정리한다.
4. 문단 경계·탭·들여쓰기·표 위치·숫자·날짜·URL·수식은 보존한다.
5. 깨진 문자나 OCR 처리 정보로 의심되는 숫자열은 지우지 않고 `quality_flags`에 표시한다.

예: `신청\u00a0기간` → `신청 기간` (`\u00a0`은 특수 공백 표시).
`신청 불가`, `10\n분`, 반복 문구는 의미나 구조를 추측해서 바꾸지 않는다.
HTML 태그처럼 보이는 `<표>`도 원래 추출기의 표 표시일 수 있어 일괄 삭제하지 않는다.

공지 제목·게시일·출처 URL을 연결하고 기존 페이지·시트·행·압축 내부 경로와
사람의 확인 기록을 보존한다. `document_extraction_status`는 파일 전체의 기존 상태이며,
개별 페이지 확인 여부와 다를 수 있다. `success`는 내용 정확성 보증이 아니다.
정리본에서 주의 표시가 추가됐어도 원래 추출 상태를 자동 변경하지 않는다.
중복 문장·파일도 이 단계에서는 삭제하지 않는다.

## 왜 이 단계가 필요한가

임베딩 모델은 PDF, HWP, XLSX 파일 자체가 아니라 파일에서 꺼낸 텍스트를 입력받는다. 따라서 파일 형식별로 텍스트를 추출하고 원본 위치를 보존해야 검색 결과에 페이지·시트·슬라이드 등의 출처를 붙일 수 있다.

## 구현

실행 명령:

    .venv/bin/sejong-extract-attachments

출력:

- `data/processed/attachments/records/{attachment_id}.jsonl`: 검색·청킹 전 단계의 텍스트 단위
- `data/processed/attachments/reports/{attachment_id}.json`: 파일별 성공 여부, 경고, 텍스트 길이

형식별 위치 정보:

- PDF: 페이지
- XLSX: 시트와 행
- DOCX: 문단 또는 표와 행
- PPTX: 슬라이드
- HWP: 문서 단위
- ZIP: 내부 파일 경로와 내부 문서 위치

ZIP은 경로 탈출, 파일 개수, 개별 크기, 총 압축 해제 크기, 중첩 깊이를 제한한다. EXE는 절대 실행하지 않는다.

- ZIP 3개: 내부 XLS 등 일부 구형 형식을 아직 읽지 못한다.
- ZIP 2개: 내부 내용이 EXE뿐이다. 보안을 위해 실행·추출하지 않았다.
- PDF 파서 경고: 회전 글자와 일부 고급 한글 인코딩은 불완전할 수 있다.
- XLSX: 수식은 수식 문자열을 보존하지만 계산 결과와 화면 배치를 완전히 재현하지 않는다.
- HWP: 텍스트는 추출하지만 현재 위치 정보가 페이지가 아니라 문서 단위다.

따라서 `success` 문서만 먼저 인덱싱할 수 있으며, `review_required`와 `failed` 문서는 OCR·변환 보완 전까지 정확한 답변 근거에서 제외하거나 경고를 동반해야 한다.
