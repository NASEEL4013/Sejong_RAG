# 프로젝트 최종 벤치마크

기준일: 2026-10-11 (한국 시간). 대상은 2025·2026 선별 인덱스와 `ask_selected` 답변 경로다.
과거 2026 단독 인덱스의 평가 수치와 섞지 않는다.

## 평가 목적과 동결

검색이 정답 근거를 찾는지, 생성 모델이 그 근거로 정확히 답하는지, 자료가 부족할 때 적절히 보류하는지를 분리한다.
공개 벤치마크 점수가 아니라 이 프로젝트 전용 한국어 질문 세트다.
사람이 작성·승인한 시험이나 실제 학생 질문의 무작위 표본은 아니다.

- 총 32문항: 답할 수 있는 질문 24개, 행동 확인 8개.
- 행동 확인은 근거 없음·조건 부족·개인정보/개인 판정·허위 답변 요구 각 2개다.
- 정답 근거는 원문에서 먼저 확인한다. 기존 평가에 사용한 공지 ID와 새 정답 공지를 분리한다.
- 코퍼스 문서 자체를 모델에서 빼는 실험은 아니다. 질문·평가 출처 분리이며 유사한 주제·문서 내용은 남을 수 있다.
- 행동 질문은 새 문구지만 미래 일정·식단·조건 부족·개인 판정 같은 시나리오를 이전 진단에서도 다뤘다. 행동 8개를 완전 무노출 독립 시험이라고 부르지 않는다.
- 질문·정답·정책·코드·원문·인덱스·실제 전달 프롬프트를 호출 전에 고정한다.
- 모델에는 질문과 검색 근거만 전달하고 정답표나 평가 지표는 전달하지 않는다.
- 결과를 본 뒤 검색·프롬프트·정답표를 수정하지 않는다. 오탐은 별도 사후 검토로 남긴다.

사전 규칙: [프로토콜](../eval/project_benchmark_protocol_v1.json).

## 무엇을 재는가

| 지표 | 뜻 | 분모·주의점 |
|---|---|---|
| Hit@1/3/5 | 상위 1·3·5묶음 안에 완전한 정답 근거가 있는가 | 답할 수 있는 24문항. 제목만 일치하면 성공이 아님 |
| MRR@5 | 첫 정답 근거가 얼마나 앞에 있는가 | 1위 1점, 2위 1/2점, 5위 밖 0점의 24문항 평균 |
| 답변 정확도 | 질문의 모든 핵심 조건·사실을 정확히 답했는가 | 24문항 전체. 답변 보류·일부 누락도 성공으로 세지 않음 |
| 답변 제공률 | 답할 수 있는 질문에 실제로 답했는가 | `answered` 문항/24; 정확도와 함께 봐야 함 |
| 근거 충실도 | 각 주장을 실제 인용한 본문이 뒷받침하는가 | 생성된 모든 claim을 대조; 인용 번호가 있다는 것과 다름 |
| 행동 성공률 | 근거가 없거나 조건이 부족할 때 올바르게 대응하는가 | 8문항 전체. 상태 코드만 맞아서는 충분하지 않음 |
| 지연·사용량 | 답변까지 얼마나 걸리고 얼마나 입력·출력했는가 | 초기 로딩과 질문별 시간을 분리; 실제 SDK 사용량 기록 |

관련 문서 전체의 완전한 정답 목록을 갖고 있지 않으므로 Hit@5를 Recall@5라고 부르지 않는다.
문구 포함 자동 검사는 동의어를 놓치거나 부정문을 잘못 통과시킬 수 있다.
따라서 자동 결과는 그대로 보존하고, 답변 의미와 모든 claim의 인용 근거는 assistant가 별도로 대조한다.
이 검토도 사람의 정답 판정을 대체하거나 전체 서비스 정확도를 보장하지는 않는다.

검색·답변·근거 충실도를 분리하는 설계는 [정보검색 평가 교재](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html)와
[RAGAS 논문](https://aclanthology.org/2024.eacl-demo.16/)의 평가 관점을 참고했다.
RAGAS 패키지를 실행한 점수는 아니며, 이번에는 소규모 고정 정답과 주장별 원문 대조를 사용한다.

## 비교와 사전 참고 목표

벡터 검색만 하는 `vector`와 현재의 `vector_context`를 동일한 상위 5개·묶음당 512·합계 2,200 E5 토큰 예산으로 비교한다.
기준선에서는 인접 문맥을 붙이지 않는다. Gemini 답변은 현재 경로에 대해서만 생성한다.
따라서 기준선 대비 답변 생성 정확도가 개선됐다는 결론은 내리지 않는다.

결과를 보기 전에 정한 학습용 참고 목표는 Hit@5 80% 이상 및 기준선 대비 비하락,
답변 정확도 80% 이상, claim 근거 충실도 95% 이상, 행동 확인 8/8이다.
작은 표본의 임의 참고 목표이지 검증된 실서비스 배포 기준은 아니다.
목표를 못 채워도 결과를 숨기거나 시험 문제를 고쳐 통과시키지 않고, 실패 유형과 남은 개선점을 기록한다.

## 재현 방법

```bash
# 로컬 검색 평가와 프롬프트 저장만 수행
.venv/bin/python -m sejong_rag.benchmark --output-dir data/processed/benchmark-new-offline

# 실제 Gemini 답변까지 평가: 새 폴더 필수, API 사용량 발생
.venv/bin/python -m sejong_rag.benchmark --output-dir data/processed/benchmark-new-live --live
```

실행에 필요한 수집 자료·정리본·선별 청크·인덱스와 로컬 E5 모델이 있어야 한다.
Gemini는 기존 `GEMINI_API_KEY` 또는 `GOOGLE_API_KEY`를 사용한다. 키 값은 기록하지 않는다.
동일 입력을 보존해도 외부 모델의 답변과 지연은 재실행마다 달라질 수 있다.
초기 준비 시간, 질문 임베딩을 포함한 검색 시간, 생성 시간, 실제 입력·출력 토큰을 따로 해석한다.
벤치마크는 모델을 한 번 불러와 여러 질문을 연속 처리한다. 현재 CLI를 질문마다 새로 실행하면
초기 로딩이 매번 추가되므로 warm 지연만 보고 실제 터미널 대기 시간을 예상하면 안 된다.

원본 `report.json`의 자동 결과는 수정하지 않는다. 각 질문의 `answer_correct` 또는 `behavior_correct`,
모든 `claim_checks`의 실제 인용 번호·지원 여부·이유를 별도 리뷰 JSON에 기록한 뒤 합산한다.
리뷰는 해당 원본 보고서 SHA-256에 묶이며, 질문 누락·중복·인용 매핑 변경·사후 프로토콜 변경은 거부한다.

```bash
.venv/bin/python -m sejong_rag.finalize_benchmark \
  --report data/processed/project-benchmark-v1-resumed/report.json \
  --reviews eval/project_benchmark_review_a_v1.json eval/project_benchmark_review_b_v1.json \
  --output-dir data/processed/benchmark-review-new
```

이 명령은 기존 리뷰를 검증·합산할 뿐 새로운 답변의 의미를 자동 심사하지 않는다.
새 실행은 답변이 달라질 수 있어, 예전 리뷰를 새 보고서에 그대로 적용할 수 없다.

## 최종 결과

같은 24개 정답 가능 질문의 사전 고정 문구·공지 범위 기준이다.
완전한 답 문구가 **한 근거 묶음**에 함께 있어야 성공으로 세며, 제목은 근거에 포함하지 않는다.

| 검색 지표 | 벡터만·동일 예산 | 현재 인접 문맥 보완 |
|---|---:|---:|
| Hit@1 | 8/24 (33.3%) | 12/24 (50.0%) |
| Hit@3 | 11/24 (45.8%) | 15/24 (62.5%) |
| Hit@5 | 11/24 (45.8%) | 15/24 (62.5%) |
| MRR@5 | 0.3889 | 0.5556 |

B13·B14·B16·B24에서 추가 성공했고, 기존 성공을 잃은 경우는 없었다.
다만 복합 질문의 정답 조각이 여러 묶음에 분산되면 이 엄격한 검색 지표는 실패로 센다.
B07·B10·B15·B17이 그 사례다. 모델은 여러 근거를 함께 읽으므로 단일 묶음 Hit@5와 답변 정확도가 같을 필요는 없다.
이를 이유로 원래 검색 점수를 사후 수정하지 않는다.

| 현재 경로 답변 지표 | 결과 |
|---|---:|
| 사전 rubric 기준 완전한 정답 | 18/24 (75.0%) |
| 답할 수 있는 질문에 답변 제공 | 20/24 (83.3%) |
| 답변한 질문 중 완전한 정답 | 18/20 (90.0%) |
| 생성된 `claims`의 실제 인용 본문 지원 | 46/47 (97.9%) |
| `claims`의 유효 인용 번호 보유 | 47/47 (100%) |
| 보류·조건 확인·개인정보·허위 답변 요구 대응 | 8/8 (100%) |

위의 의미 판정은 assistant의 주장별 원문 대조이며 사람 승인 결과가 아니다.
자동 문구·상태·인용 proxy 전체 통과는 21/32로 별도 보존했다.
B03·B19는 동의 표현, B07·B15·B17은 여러 근거 조합을 자동 검사가 놓친 사례다.
기존 12문항 진단이나 과거 인덱스의 평가와 문제·난도·지표가 달라 직접적인 성능 추세로 비교할 수 없다.

### 남은 실패와 해석

- B01·B02·B05: 환불 구간, 포털 메뉴, 해당 연도 적용 조건 등 필요한 일부 근거를 찾지 못해 답변을 보류했다.
- B10: 추가 지급액 **50만원 계산은 맞았다**. 다만 사전에 정한 rubric이 요구한 ‘차액 지급 1회 한정’을 답변에서 빠뜨려 엄격한 완전 정답 기준에서는 실패다. 계산 오답으로 해석하지 않는다.
- B12: 전화번호는 찾았지만 이메일을 놓쳤고, 일부 청크만 보고 ‘안내 자료에는 이메일이 없다’고 문서 전체의 부재를 단정했다. 해당 claim은 지원되지 않는 것으로 판정했다.
- B21: 신청 기한은 찾았지만 가구원 재동의 예외를 놓쳤다. 또한 보류 상태의 `message`에 날짜 사실을 인용 없이 넣어 출력 규칙을 어겼다.

B21은 중요한 측정 한계다. `claims` 배열이 비어 있으므로 47개 claim의 인용 검사 분모에는 들어가지 않는다.
따라서 claim 인용 번호 100%를 **모든 출력에 인용 누락이 없었다**는 뜻으로 해석하면 안 된다.
이 메시지 사실 누출은 별도 검토 항목으로 기록했으며 이번 시험 결과를 보고 생성 코드를 다시 조정하지 않았다.

모든 정답 원문은 HTML 공지 본문이다. 검색에서는 관련 첨부도 사용할 수 있지만,
이 벤치마크가 첨부에만 있는 답이나 OCR 정확도까지 독립적으로 검증한 것은 아니다.

### 속도·사용량·운영 오류

생성 모델은 `gemini-3.5-flash-lite`, 응답 출력 상한은 1,600토큰이었다.

- 초기 모델·인덱스 로딩: 19.68초.
- 질문 임베딩과 요청 구성을 포함한 warm 검색: 중앙값 83.6ms, p95 95.7ms.
- 검색+생성의 질문별 합: 중앙값 1.65초, p95 2.19초. 초기 로딩과 재개 조사·대기 시간은 제외했다.
- API 호출 33회 중 응답 수신 32회, 오류 1회. 응답에서 확인된 입력 85,623토큰·출력 3,906토큰, 합계 89,529토큰.
- 실패한 호출 1회의 사용량은 알 수 없다. 위 합계를 실제 청구 총량으로 확정하지 않는다.

최초 실행은 B17에서 공급자 `ClientError`로 중단됐다. 최초 오류의 세부 코드가 저장되지 않아 정확한 원인은 확정하지 않는다.
완료된 B01~B16은 그대로 보존하고, 미완료 B17~B32의 같은 동결 프롬프트만 새 실행에서 이어갔다.
질문별 총 2회·전체 64회 상한을 지켰으며, 재개 후 32문항 모두 완료했다.
검색·생성 코드, 모델·출력 길이, 질문·정답표는 바꾸지 않았다. 원본·코드·프롬프트 해시도 실행 후 일치했다.
복구 도구는 동결 후 추가한 평가 운영 도구이며, 이 추가와 두 실행의 연결 정보를 별도로 저장했다.

```bash
# 최초 실행이 외부 API 오류로 중단됐을 때만 사용한다. 새 폴더 필수.
.venv/bin/python scripts/resume_frozen_benchmark.py \
  --report data/processed/project-benchmark-v1/report.json \
  --output-dir data/processed/benchmark-resume-new
```

이미 완료한 답을 다시 뽑아 좋은 결과를 선택하는 방식이 아니다.
완료된 평가를 위 최초 부분 보고서에서 다시 이어갈 필요는 없다. 실제 보존된 재개 결과를 사용한다.

## 마무리 판정

학습용 CLI RAG의 구현·평가·재현 문서는 마무리한다. 다만 검색 Hit@5와 완전 답변 정확도는
사전에 정한 80% 참고 목표에 미달했다. 근거 충실도와 행동 목표를 충족했다고 실서비스 준비가 끝난 것은 아니다.
전체 코드 테스트는 456개 통과했다. 이는 코드 동작 검사이며 답변 정확도 456/456을 뜻하지 않는다.

남은 개선 과제는 복합 질문의 여러 근거 확보, 제목·부분 문맥 편중, 원문 구조·취소선 보존,
보류 메시지의 사실·인용 검사, 실제 학생 질문과 첨부 전용/OCR 근거 평가다.
검색·프롬프트를 더 튜닝하면 이 시험은 개발 데이터로 분류하고 새로운 시험 세트를 마련해야 한다.
웹 화면, 공개 배포, 개인 학적 조회, 실시간 학교 정보 수집은 이번 완료 범위가 아니다.
