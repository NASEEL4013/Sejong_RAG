# 임베딩·벡터 검색 기준선
> 역사적 단계 기록: 이 문서는 개발 당시의 구현과 수치를 보존한다. 현재 상태와 실행 방법은 [프로젝트 README](../README.md) 및 [문서 지도](README.md)를 기준으로 한다.


## 목적

키워드가 정확히 일치하지 않아도 의미가 비슷한 수강편람 chunk를 찾을 수 있는지 확인한다. 이 단계는 답변을 생성하는 LLM이 아니라, 답변 근거 후보를 찾는 retrieval 단계다.

## 선택한 모델

- 모델: `intfloat/multilingual-e5-small`
- 용도: 질문과 문서 검색에 맞춰 학습된 다국어 임베딩 모델
- 벡터 차원: 384
- 최대 입력: 512 tokens
- 입력 규칙: 질문은 `query:`, 문서는 `passage:` 접두사 사용
- 벡터 정규화: 사용
- 검색 점수: 정규화된 질문·문서 벡터의 내적, 즉 cosine similarity

첫 기준선에서는 CPU로 실행하기 쉽고 검색용으로 학습된 작은 모델을 선택했다. 이 선택이 한국어 대학 행정 문서에 가장 정확하다고 가정하지 않으며 평가 결과로 재검토한다.

## 생성 결과

- 원본 chunk: 530개
- 벡터 행렬: 530 x 384
- 저장 형식: 압축 NumPy `.npz`
- 토큰 길이: 최소 21, 최대 790
- 512 tokens 초과: 178/530 (33.6%)
- 인덱스: `data/index/notice3-891485-e5-small.npz`

512 tokens를 넘는 chunk는 모델 입력의 뒤쪽이 잘린다. 따라서 이 인덱스는 구조 확인용 첫 baseline이며 최종 인덱스가 아니다.

## 대표 질문 결과

| 질문 | 기대 근거 | 벡터 검색 순위 | 이전 키워드 순위 | 판정 |
|---|---:|---:|---:|---|
| 소프트웨어학과 졸업학점 | 입학년도별 졸업학점 표 | 관련 표 1위, 명확한 소프트웨어학과 행은 3위 이후 | 관련 근거 1위 | 조건 구분 부족 |

| 재수강 성적 | 34쪽 | 1위 | 1위 | 성공 |

코사인 점수는 정답 확률이 아니다. 현재 결과에서는 오답 chunk도 0.86 이상의 높은 값을 보여 절대 임계값만으로 정답을 판별하면 위험하다.

## 해석

1. 문자 1,600자 기준 chunk와 모델의 512-token 제한이 맞지 않는다.
2. 표가 큰 chunk 안에 여러 학과와 숫자를 포함해 하나의 벡터에 여러 의미가 섞인다.
3. 페이지 상단 문맥을 모든 chunk에 반복해 서로 다른 chunk가 지나치게 비슷해질 수 있다.
4. 작은 다국어 모델이 한국어의 모든 우회 표현을 안정적으로 연결하지는 못한다.
5. 임베딩 검색도 평가 질문과 정답 근거가 있어야 개선 여부를 판단할 수 있다.

## 다음 실험

- E5 tokenizer 기준으로 512 tokens를 넘지 않도록 재청킹한다.
- 제목 문맥은 유지하되 대형 표는 행 또는 작은 묶음 단위로 분리한다.
- 같은 네 질문으로 다시 평가해 baseline과 순위를 비교한다.
- 이후 키워드 점수와 벡터 점수를 합치는 hybrid search를 실험한다.

## TOKEN-001: E5 토큰 기준 재청킹

### 변경

- 기준: 문자 1,600자 → E5 tokenizer 448 tokens
- overlap: 문자 200자 → 64 tokens
- 페이지 상단 5줄 반복 제거
- 원문 offset으로 잘라 PDF 줄바꿈과 공백 보존
- 기존 기준선 데이터와 인덱스는 비교를 위해 보존

### 결론

토큰 재청킹은 모델이 읽지 못하는 텍스트를 없앴지만 의미 검색의 모든 오류를 해결하지는 못했다. 관련 페이지가 높은 순위에 있어도 정답 문장이 든 chunk가 낮을 수 있으므로 평가는 페이지 단위와 정답 chunk 단위를 구분해야 한다.

다음 실험은 키워드 점수와 벡터 점수를 결합하는 hybrid search다. 또한 평가 질문에 입학년도처럼 답을 결정하는 조건이 빠졌다면 시스템이 임의로 하나를 고르지 않고 사용자에게 되묻도록 설계한다.
