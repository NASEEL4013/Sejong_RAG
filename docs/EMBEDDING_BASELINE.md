# 임베딩·벡터 검색 기준선

## 선별 인덱스 검색 개선 (2026-10-11)

기본 검색 경로는 `sejong_rag.selected_search`이며, **벡터 검색 + 제한된 인접 문맥 보완**을 사용한다.
임베딩 모델과 33,734개 벡터는 그대로 유지했다. 기존 답변 생성 경로의 기본값은 변경하지 않았다.

### 진단한 원인

- 짧은 소제목과 설명이 서로 다른 청크로 분리되었다. S15에서는 납부확인 제목이 2위, 실제 확인 시점은 13위였다.
- 본문 100자 미만 청크가 8,060개(23.9%)였다. S15의 제목 청크는 본문 38자에 비해 문서 제목·파일명이 길어, 전체 글자의 약 80%가 제목 계열이었다.
- 같은 공지를 찾는 것과 답을 담은 문장을 찾는 것은 달랐다. S17 제출처 질문은 관련 공지의 다른 조각이 앞서고, 직접 답은 14위였다.
- 연도·학기가 다른 유사 공지, HTML·PDF의 반복, 계절학기 표현 차이도 남아 있다. 모든 원인을 해결했다는 의미는 아니다.

### 기본 적용한 개선

1. 기존 벡터 순서에서 후보를 가져온다. 질문 임베딩은 동일한 E5 모델과 `query: ` 접두어를 사용한다.
2. 본문이 E5 기준 100토큰 이하이면 같은 정리본 기록의 바로 다음·이전 청크를 확인한다. 원문 구간 간격은 최대 10자이며 다른 기록·공지·페이지를 넘지 않는다.
3. 제목과 본문을 합친 근거 한 묶음은 최대 512토큰, 최대 5묶음의 합계는 2,200토큰으로 제한한다. 이웃을 붙이면 남은 예산을 넘는 경우 원래 근거를 유지한다.
4. 같은 공지 범위에서 충분히 긴 조립 본문이 동일한 경우만 중복을 제거한다. 중복 사본의 청크 ID·원문 위치·출처도 보존한다.
5. 선택 청크와 정리본의 내용 지문 및 원문 위치를 검증한다. 원본 데이터·청크·벡터를 수정하지 않는다.

여기서 5개는 항상 원래 청크 5개를 뜻하지 않는다. 짧은 청크와 인접 설명을 합친 **근거 묶음 최대 5개**다.
토큰 제한은 E5 기준 제목·본문 합계이며, JSON 메타데이터나 답변 모델의 전체 프롬프트 한도를 뜻하지 않는다.
보고서는 근거 번호를 붙인 직렬화 텍스트의 토큰 수도 별도 기록한다.

### 키워드 결합을 기본값에서 제외한 이유

본문만의 문자 2~3그램 TF-IDF와 벡터 순위를 가중 RRF로 합치는 방식도 구현했다.
명시된 연도·학기를 연결된 모든 공지 출처와 비교하고, 직접 답을 포함할 수 있는 벡터 1위 후보를 보존하는 보완도 포함했다.
검색어 확장에는 장소·기간 같은 일반 용어만 쓰며 정답 값이나 특정 공지 번호를 넣지 않는다.

개발 20문항에서는 결합 검색 + 문맥 보완이 1위 60%, 상위 5개 100%였다.
하지만 별도 검증 20문항에서는 상위 5개 80%로 기존과 같았고, 1위 비율은 55%에서 50%로 낮아졌다.
한 문항을 새로 맞히는 대신 기존 성공 한 문항을 놓쳤다. 따라서 이 경로는 실험 옵션 `--strategy improved`로만 남겼다.
RRF 점수는 정답 확률이 아니며, 후보 보존 규칙 적용 후 반환 순서와 점수 내림차순은 다를 수 있다.

기본값 `vector_context`는 검증 20문항의 기존 성공 여부와 정답 순위를 모두 보존했다.
이 20문항은 최종 전략 선택에 사용했으므로 **검증용**으로 분류하고, 마지막 확인용 문항은 따로 만들었다.
전략 선택 기록은 `eval/selected_retrieval_release_v1.json`, `selected_retrieval_release_v2.json`에 남아 있다.

### 실행과 평가 재현

```bash
.venv/bin/python -m sejong_rag.selected_search "2026년 2학기 등록금 납부 확인은 언제 가능해?"

.venv/bin/python -m sejong_rag.compare_selected \
  --cases eval/selected_retrieval_v1.jsonl \
  --audit eval/selected_retrieval_v1_audit.json \
  --output-dir data/processed/evaluation-selected-compare-rerun
```

비교 전략은 `vector`, `hybrid`, `vector_context`, `improved`다. 평가 출력 폴더는 매번 새 경로여야 한다.
순수 벡터 기준선은 원래 인덱스의 상위 5개를 그대로 사용한다. 모든 방식에 같은 본문·출처 정답 기준을 적용한다.
평가 전에 질문·근거·원문·코드 지문을 고정하고, 종료 시 변조 여부를 확인한다.
기존 S08의 대체 정답은 개발 평가 모든 방식에 동일하게 적용하며 원래 평가 기록은 덮어쓰지 않는다.

| 비교 자료 | 기존 상위 5개 정답 포함 | 기본 개선 후 | 기존 / 개선 MRR@5 |
|---|---:|---:|---:|
| 개발 20문항 | 18/20 (90%) | 20/20 (100%) | 0.5925 / 0.6425 |
| 전략 선택 검증 20문항 | 16/20 (80%) | 16/20 (80%) | 0.6392 / 0.6392 |
| 마지막 새 20문항 — 사전 고정 자동 기준 | 13/20 (65%) | 14/20 (70%) | 0.4958 / 0.5083 |
| 마지막 새 20문항 — 원문 대조 후 보완 | 15/20 (75%) | 16/20 (80%) | 0.5958 / 0.6458 |

MRR@5는 상위 5개 밖을 0점으로 계산한다. 아래의 과거 전체 순위 MRR과는 정의가 다르다.
기본 개선의 개발 문항 결과는 **S15: 13위 원본 청크 → 2위 근거 묶음, S17: 14위 원본 청크 → 2위 근거 묶음**이다.
원래 청크 자체의 벡터 순위가 바뀐 것이 아니라, 전달 근거에 인접 답 문장이 들어간 결과다.
개발 문항에서 근거 텍스트는 평균 약 726→955토큰, 준비 완료 후 검색은 평균 약 9ms였다.
시간에는 모델·인덱스 준비, 질문 임베딩, 답변 생성이 포함되지 않는다.

- 개발 비교: `data/processed/evaluation-selected-compare-v1/index.html`
- 결합 검색의 첫 독립 시험: `data/processed/evaluation-selected-holdout-v1/index.html`
- 기본값 선택용 문맥 보완 비교: `data/processed/evaluation-selected-validation-context-v1/index.html`
- 마지막 새 문항 자동 평가: `data/processed/evaluation-selected-final-holdout-v1/index.html`
- 마지막 새 문항 사후 대조 기록: `eval/selected_retrieval_final_holdout_v1_audit.json`

마지막 20문항은 앞선 두 세트와 겹치지 않는 15개 공지에서 작성했고, 기본값을 고른 뒤 한 번만 검색했다.
이후 검색 설정은 바꾸지 않았다. 자동 실패와 새 성공 문항을 원문 대조해 다음을 별도 기록했다.

- F03: 원래 상위 5개에는 K-MOOC 인정 한도가 없었다. 개선 후 1위 묶음에 인접 문장을 붙여
  ‘학기당 3학점, 졸업까지 최대 6학점’을 확보했다. 자동 채점은 다른 공식 출처의 동등한 표현을 놓쳐 4위로 계산했다.
- F15·F16: 첨부파일은 ‘지원금액’ 대신 ‘장학금액’이라고 표현했지만 금액·조건을 정확히 담고 있었다.
  두 방식 모두 1위의 동등한 정답으로 인정했다. 기존 질문이나 자동 결과를 덮어쓰지 않았다.
- 나머지 F05·F06·F09·F14는 양쪽 모두 필요한 답을 놓쳤다. 관련 공지의 다른 절, 다른 학기 자료,
  수강편람의 유사 규칙이 실제 답 문장보다 앞서는 문제가 남았다.

사후 대조는 고정 자동 평가와 별도이며, 전체 코퍼스의 모든 동등한 근거를 완전하게 판정한 결과는 아니다.
마지막 20문항에서 기존 성공을 잃은 경우는 없었다. 근거 텍스트는 평균 859→1,085토큰,
최대 1,921토큰이었다. 테스트는 전체 259개 통과했다.

적은 수의 보조 작성 문항과 문구 일치 라벨에 의한 진단이다. 전체 서비스 정확도, 답변 생성 품질,
자료에 답이 없는 질문이나 모호한 질문에 대한 성능은 검증하지 않았다.

## 선별 인덱스 검색 품질 진단 (2026-10-11)

실행: `.venv/bin/python -m sejong_rag.evaluate_selected`.
같은 출력 폴더가 있으면 중단하므로 재실행은 `--output-dir`로 새 폴더를 지정한다.
대상은 전날 생성한 33,734개 청크의 순수 벡터 검색이며, 검색 방식·청킹·임베딩은 변경하지 않았다.

### 평가 절차

1. `eval/selected_retrieval_v1.jsonl`에 질문 20개와 정답 문구·공지 범위를 먼저 작성했다.
2. 저장된 원본 HTML에서 정답 문구를 검증했다. 특정 공지의 제목만 일치하는 것은 정답으로 세지 않았다.
3. 원래 기록의 본문 위치로 정답 청크를 지정하고 `ground_truth.json`에 고정한 뒤 질문을 임베딩했다.
4. 인덱스 전체를 점수순으로 정렬해 최초 정답 순위와 상위 1·5개 성공률을 계산했다.
5. 자동 실패 세 문항의 상위 결과를 원문과 대조했다. 동등한 정답 누락 하나를 별도 보완 기록에 남겼다.

| 기준 | 1위에 정답 근거 | 상위 5개에 정답 근거 | MRR |
|---|---:|---:|---:|
| 사전 고정 자동 문구·공지 기준 | 8/20 (40%) | 17/20 (85%) | 0.5503 |
| 자동 실패 원문 대조 후 보완 | 9/20 (45%) | 18/20 (90%) | 0.5999 |

MRR은 최초 정답 순위의 역수 평균이다. 1위는 1점, 2위는 1/2점, 5위는 1/5점으로
가까이 검색할수록 높아진다. 여기서는 상위 5개 밖이라도 전체 순위를 사용했다.
20문항 모두 정답 근거가 인덱스 안에 존재했다.

### 실패와 평가 기준 누락

- S08 복학 완료 조건: 지정한 복학 공지 근거는 144위였지만,
  같은 학기 휴학·복학 추가 신청 공지의 1위 청크가 수강신청과 등록금 납부 모두 필요하다고 정확하게 안내했다.
  `notice3-891420` 원본 HTML로 확인하고 동등한 정답으로 인정했다.
  기존 자동 결과를 덮어쓰지 않았으며 사후 보완 점수라는 사실을 구분했다.
- S15 등록금 납부 확인 시점: 직접 답인 다음 근무일 오전 10시는 13위.
  ‘등록금 납부확인’과 실시간 확인 불가 안내는 2위지만 시점 설명과 별개 청크였다.
- S17 성적향상장학금 제출처: 학생지원과 집현관 104호 방문 제출은 14위.
  상위에는 같은 장학금의 제목·기간·양식·자격 등이 나왔다.

관찰상 해당 문서를 찾는 것과 답 문장을 찾는 것이 다르다. 짧은 소제목 청크와 상세 문장이
분리된 구조, 재정렬과 키워드 결합은 향후 개선 후보이며 이번에 개선 효과를 검증한 것은 아니다.

### 해석 범위와 산출물

이번 20문항은 9개 공지에서 구성한 학습용 개발 기준선으로, 전체 서비스 정확도나 독립 평가 점수가 아니다.
전자출결 앱 질문 S01은 이전 작동 확인에도 사용했다. 신규 19문항만의 자동 상위 5개 성공률은 16/19이다.
모호한 질문·답이 없는 질문·답변 생성은 이번 평가 대상이 아니다.
문구 일치 기반 자동 정답은 모든 동등한 표현을 망라하지 못하므로 S08처럼 누락이 생길 수 있다.
향후 개선에 이 문항들을 쓰면 최종 확인용 질문은 별도로 준비해야 한다.

- 질문: `eval/selected_retrieval_v1.jsonl`
- 사후 근거 보완: `eval/selected_retrieval_v1_audit.json`
- 자동 결과: `data/processed/evaluation-selected-v1/report.json`
- 대조 후 결과: 같은 폴더의 `reviewed-report.json`
- 질문별 상위 5개와 정답 비교 화면: 같은 폴더의 `index.html`
- 평가 코드: `src/sejong_rag/evaluate_selected.py`

원본·인덱스·평가 질문 파일의 내용 지문이 실행 전후 일치했으며 전체 테스트 204개를 통과했다.

## 2025·2026 선별 청크 임베딩 (2026-10-10)

새 실행기는 `sejong_rag.embed_selected`다. 기존 역사적 인덱스는 덮어쓰지 않는다.

    HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 .venv/bin/python -m sejong_rag.embed_selected

- 입력: `data/processed/selected-chunks/selected.jsonl`의 일반 추출 청크 33,734개.
- 모델: 로컬에 저장된 `intfloat/multilingual-e5-small`. 외부 API로 문서를 전송하지 않는다.
- 문서는 `passage: `, 질문은 `query: ` 접두어를 붙인다.
- 입력 검사: 접두어·특수 토큰 포함 16~450토큰, 모델 한도 512, 잘림 예상 0개.
- 청크마다 384차원 벡터를 만들고 길이를 1로 정규화한다.
- 중간 저장: `data/processed/embedding-selected-e5`에 512개씩 저장한다.
  같은 명령으로 재시작하면 완료 구간을 재사용하되 입력 지문이나 설정이 다르면 중단한다.
- 최종 출력: `data/index/sejong-2025-2026-selected-e5-small.npz`.
  완성된 인덱스가 이미 있으면 덮어쓰지 않는다.
- 벡터 개수·차원·유한한 수인지 여부·정규화·원본 청크 지문을 검사한다.
- 청크 본문, 원문 위치, 연결된 모든 공지 출처는 인덱스에 함께 저장한다.

임베딩은 모델을 새로 학습하는 것이 아니다. 기존 모델로 문서를 숫자 배열로 변환하는 작업이다.
인덱스는 벡터와 그에 해당하는 청크·출처를 묶어 검색할 수 있게 저장한 파일이다.
출처 별칭은 공지마다 제목·게시일이 다를 수 있으므로 대표 제목을 모든 공지에 적용하면 안 된다.

완료 후 새 인덱스를 명시하여 검색:

    .venv/bin/python -m sejong_rag.vector_search "휴학은 어떻게 신청하나요?" --index data/index/sejong-2025-2026-selected-e5-small.npz --local-files-only --top-k 5

기존 답변 생성 서비스의 기본 인덱스는 바꾸지 않는다. 이 단계의 시험은 순수 벡터 검색이며,
정확한 날짜·학기 필터나 키워드 결합, 답변 생성까지 검증한 것은 아니다.
실행 완료 후 `data/processed/embedding-selected-e5/report.json`에 세 질문의 상위 5개 검색 결과가 남는다.

## 목적

키워드가 정확히 일치하지 않아도 의미가 비슷한 수강편람 chunk를 찾을 수 있는지 확인한다. 이 단계는 답변을 생성하는 LLM이 아니라, 답변 근거 후보를 찾는 retrieval 단계다.

## 선택한 모델

- 모델: `intfloat/multilingual-e5-small`
- 용도: 질문과 문서 검색에 맞춰 학습된 다국어 임베딩 모델
- 벡터 차원: 384
- 최대 입력: 512 tokens
- 입력 규칙: 질문은 `query:`, 문서는 `passage:` 접두사 사용
- 벡터 정규화: 사용
- 검색 점수: 정규화된 질문·문서 벡터의 내적, 즉 cosine similarity

첫 기준선에서는 CPU로 실행하기 쉽고 검색용으로 학습된 작은 모델을 선택했다. 이 선택이 한국어 대학 행정 문서에 가장 정확하다고 가정하지 않으며 평가 결과로 재검토한다.

## 해석

1. 문자 1,600자 기준 chunk와 모델의 512-token 제한이 맞지 않는다.
2. 표가 큰 chunk 안에 여러 학과와 숫자를 포함해 하나의 벡터에 여러 의미가 섞인다.
3. 페이지 상단 문맥을 모든 chunk에 반복해 서로 다른 chunk가 지나치게 비슷해질 수 있다.
4. 작은 다국어 모델이 한국어의 모든 우회 표현을 안정적으로 연결하지는 못한다.
5. 임베딩 검색도 평가 질문과 정답 근거가 있어야 개선 여부를 판단할 수 있다.

## 다음 실험

- E5 tokenizer 기준으로 512 tokens를 넘지 않도록 재청킹한다.
- 제목 문맥은 유지하되 대형 표는 행 또는 작은 묶음 단위로 분리한다.
- 같은 네 질문으로 다시 평가해 baseline과 순위를 비교한다.
- 이후 키워드 점수와 벡터 점수를 합치는 hybrid search를 실험한다.

### 결론

토큰 재청킹은 모델이 읽지 못하는 텍스트를 없앴지만 의미 검색의 모든 오류를 해결하지는 못했다. 관련 페이지가 높은 순위에 있어도 정답 문장이 든 chunk가 낮을 수 있으므로 평가는 페이지 단위와 정답 chunk 단위를 구분해야 한다.

다음 실험은 키워드 점수와 벡터 점수를 결합하는 hybrid search다. 또한 평가 질문에 입학년도처럼 답을 결정하는 조건이 빠졌다면 시스템이 임의로 하나를 고르지 않고 사용자에게 되묻도록 설계한다.
